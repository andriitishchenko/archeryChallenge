# Runtime operations

## FEAT-OPS-001 — Safe production startup and readiness

- Status: Partial
- Scope: `backend/core/config.py`, `backend/models/database.py`, `backend/migrations/`, `backend/main.py`, startup scripts, and the container entry point.
- Goal / acceptance: Refuse unsafe production configuration before serving requests, preserve existing data when the schema is incompatible, and report database readiness accurately.
- Expected behavior and invariants: Production requires an explicit strong JWT secret, TLS-enabled PostgreSQL, HTTPS reset-link base URL, configured mail delivery, and debug documentation disabled. Cross-origin deployments use explicit HTTPS CORS origins; same-origin deployments may leave CORS empty. An empty schema may be initialized for a fresh database; an unversioned, older, newer, or structurally different existing schema stops migration without changing application rows. Health reports unavailable when the database cannot answer. Deployment uses the repository root as Docker build context and one worker until process-local WebSocket, rate-limit, and expiry state is shared.
- Enforcement and current behavior: Production startup → validates the signing key, TLS PostgreSQL URL, HTTPS application URL, explicit HTTPS CORS origins when cross-origin access is used, real sender address, SMTP/TLS, and positive limits → unsafe settings stop before serving requests. Deployment entry points apply Alembic migrations before Uvicorn starts; runtime verifies `schema_version`, the migration head, and SQLAlchemy table/index metadata. The baseline creates an empty database or adopts a version-5 database only when metadata matches; incompatible databases fail without changing application rows. `/health` returns 503 when `SELECT 1` fails. The Docker image uses the repository root context, runs as a non-root user, uses one worker, disables Uvicorn access logs, and caps WebSocket messages at 64 KiB.
- Regression coverage: `backend/tests/test_production_guards.py` covers production settings, bounded per-client rate limiting, and WebSocket guards. `backend/tests/test_database_migrations.py` covers fresh schema creation, safe current-schema adoption, rejection of an older schema while preserving rows, and startup detection of schema drift. A migrated SQLite database also passed an app lifespan startup check. Container and live PostgreSQL startup were not run in this environment.
- Remaining limits: Only the baseline migration exists; older or structurally different databases require an explicitly reviewed migration before deployment. PostgreSQL backup/restore, SMTP delivery, TLS proxy behavior, and multi-instance operation still require deployment-level configuration and verification. Process-local realtime, matchmaking, rate-limit, and expiry state requires one worker.
